# SplitLa 第一版

Status: ready-for-agent

詞彙跟 `CONTEXT.md`。本文所有粗體英文詞都係嗰度定義嘅。

## Problem Statement

一班朋友出街食飯、去旅行，通常有人先畀錢，之後要計返邊個欠邊個。現有嘅分帳 App 只處理已經洗咗嘅錢。

真正令人後悔嘅決定發生喺洗錢之前：朋友提議去一間每人 $800 嘅餐廳，你唔知夾埋今個月已經應承咗嘅飯局會唔會超出自己負擔得起嘅範圍，又唔想喺群組度講自己預算有幾多。結果通常係照去，月尾先發現超支。

## Solution

SplitLa 係一個 iPhone 分帳 App，有兩部分：

1. **分帳**：記錄 **Expense**，計出每個 **Member** 喺 **Group** 入面嘅 **Balance**，建議點樣用最少次數嘅轉帳找清，並記錄 **Settlement**。
2. **預算檢查**：朋友喺 **Activity** 入面開 **Proposal**。每個成員即時見到一個 **What-if Check**：呢個提案會唔會超出 **Activity Budget**（全組可見），同埋會唔會令自己今個月嘅 **Committed Spend** 超出 **Personal Budget**（只有本人可見）。

個人預算永遠唔離開用戶自己嘅裝置同 iCloud。其他成員同 SplitLa 嘅 server 都唔知道佢嘅數值，亦唔會知道邊個超咗支。

## User Stories

### 帳戶、群組、成員

1. 作為新用戶，我想用 email 驗證碼登入（之後加 Sign in with Apple），咁我唔使記多一個密碼。
2. 作為用戶，我想開一個 **Group** 並改名，咁我同一班固定嘅朋友可以長期用同一個地方記數。
3. 作為 **Member**，我想產生一條邀請連結再用 WhatsApp 傳出去，咁朋友撳一下就加入到群組。
4. 作為收到邀請連結嘅人，我想撳連結之後直接加入群組，咁我唔使搵群組代號。
5. 作為 **Member**，我想加一個得個名嘅 **Placeholder Member**，咁唔肯裝 App 嘅朋友都可以入數。
6. 作為之前被人加做 **Placeholder Member** 嘅人，我想加入群組嗰陣認領返自己個佔位，咁我之前嘅數會跟返我。
7. 作為 **Member**，我想同時屬於多個群組，咁我同唔同圈子嘅朋友可以分開記數。
8. 作為 **Member**，我想就算仲有 **Balance** 都可以退出群組，咁我唔會被迫留喺一個我唔再用嘅群組。
9. 作為留低嘅 **Member**，我想退出咗嘅人變成 **Placeholder Member** 而條數留低，咁我仍然見到佢欠幾多。

### 活動同出席

10. 作為 **Member**，我想喺群組入面開一個有名同日期嘅 **Activity**，咁相關嘅提案同開支可以放埋一齊。
11. 作為 **Organiser**，我想為活動定一個選填嘅 **Activity Budget**，咁全組知道呢次預計總共洗幾多。
12. 作為 **Organiser**，我想之後改或者移除活動預算，咁計劃變咗可以跟住改。
13. 作為 **Member**，我想對每個活動標記 **Attendance**（去、唔去、未覆），咁其他人知道有幾多人夾。
14. 作為 **Member**，我想隨時改自己嘅出席狀態，咁我改變主意嗰陣個數會跟住更新。
15. 作為 **Member**，我想見到每個活動有邊個去、邊個未覆，咁我知道份額係用幾多人計出嚟。
16. 作為 **Member**，我想代 **Placeholder Member** 標記出席狀態，咁冇裝 App 嘅朋友都計入人數。

### 提案同預算檢查

17. 作為 **Member**，我想喺活動入面開一個 **Proposal**，寫低名稱同預計金額，咁全組可以睇到呢個選擇要幾多錢。
18. 作為開提案嘅人，我想揀入「每人」金額或者「總數」，咁我可以照住我手上有嘅資料入。
19. 作為 **Member**，我想一個活動可以有多個提案並排睇，咁我哋可以比較幾間餐廳。
20. 作為 **Member**，我想見到每個提案換算之後我嘅 **Share**，咁我知道自己要畀幾多。
21. 作為 **Member**，我想見到每個提案加埋活動已有開支之後，會唔會超出 **Activity Budget** 同超幾多，咁全組有共同嘅依據去揀。
22. 作為 **Member**，我想私下定一個每月嘅 **Personal Budget**，咁 App 可以幫我睇住自己嘅上限。
23. 作為 **Member**，我想確定其他成員完全睇唔到我嘅個人預算同我有冇超支，咁我可以放心定一個真實嘅數。
24. 作為 **Member**，我想每個提案都顯示「如果去呢度，我今個月仲剩幾多」，咁我未超支都感受到自己離上限有幾遠。
25. 作為 **Member**，我想提案會令我超支嗰陣見到明顯嘅紅色警告同超支金額，咁我可以喺出發之前提出轉地方或者決定唔去。
26. 作為仲未覆去唔去嘅 **Member**，我想預算檢查以「假設我去」嚟計，咁我可以用個結果決定去唔去。
27. 作為冇定個人預算嘅 **Member**，我想預算檢查只顯示活動層面，咁我唔定預算都用到 App。
28. 作為 **Organiser**，我想揀一個提案做 **Chosen Proposal**，咁全組知道最後去邊度。
29. 作為 **Organiser**，我想改揀另一個提案或者取消選定，咁計劃變咗可以更正。
30. 作為 **Member**，我想我覆咗「去」嘅活動入面選定提案嘅份額計入我嘅 **Committed Spend**，咁之後嘅預算檢查會計埋我已經應承咗嘅飯局。
31. 作為 **Member**，我想睇到今個月嘅 Committed Spend 由邊幾筆組成，咁我明白個數點嚟。
32. 作為 **Member**，我想跨月旅行嘅每筆開支計落佢自己日期嗰個月，咁每個月嘅數字如實反映。

### 開支同分帳

33. 作為 **Member**，我想記一筆 **Expense**，寫低金額、邊個畀錢、邊啲人有份，咁 App 可以計返邊個欠邊個。
34. 作為 **Member**，我想揀平均分，咁最常見嘅情況唔使逐個入數。
35. 作為 **Member**，我想逐人入實際金額，咁各人食得唔同都分得啱。
36. 作為 **Member**，我想開「加一服務費」開關，咁我照餐牌價入數都計到實際要畀嘅金額。
37. 作為 **Member**，我想活動完咗之後將選定提案一撳轉做開支，預先填好資料，我只需要改實際金額同邊個畀錢。
38. 作為 **Member**，我想提案轉做開支之後，我嘅 Committed Spend 用實際份額取代預計份額，咁個數唔會計兩次。
39. 作為 **Member**，我想改或者刪任何一筆開支，咁入錯數唔使等原本入數嗰個人。
40. 作為 **Member**，我想睇到每筆開支嘅改動記錄（邊個、幾時、改咗乜），咁冇人可以靜靜雞改數。
41. 作為 **Member**，我想記一筆唔屬於任何提案嘅開支，咁臨時起意嘅消費都入到數。

### 結餘同找數

42. 作為 **Member**，我想見到自己喺成個群組跨晒所有活動嘅 **Balance**，咁我唔使逐個活動計。
43. 作為 **Member**，我想 App 建議一組次數盡量少嘅轉帳去找清全組嘅數，咁我哋唔使兜圈互相過數。
44. 作為 **Member**，我想記錄一筆 **Settlement**，表示我已經用 FPS 或 PayMe 畀咗錢，咁我嘅結餘會更新。
45. 作為收錢嘅 **Member**，我想見到人哋記錄咗畀我嘅找數，咁我可以對返自己戶口。
46. 作為 **Member**，我想改或者刪一筆入錯嘅找數記錄，並且留有改動記錄。

### 通知同離線

47. 作為 **Member**，我想有人開新提案嗰陣收到通知，咁我可以即刻做預算檢查。
48. 作為 **Member**，我想提案被選定嗰陣收到通知，咁我知道計劃定咗。
49. 作為 **Member**，我想有人入咗一筆有我份嘅開支嗰陣收到通知，咁我可以核對。
50. 作為 **Member**，我想有人記錄咗畀我嘅找數嗰陣收到通知。
51. 作為 **Member**，我想因為其他人改咗出席狀態、令我喺選定提案嘅份額升到超支嗰陣收到只有我見到嘅警告，咁我仲趕得切喺出發之前反應。
52. 作為 **Member**，我想冇網絡嗰陣仍然睇到上次同步嘅群組、開支同結餘，咁我喺地庫餐廳都查到數。
53. 作為 **Member**，我想冇網絡嗰陣 App 清楚話我知唔可以改嘢，咁我唔會以為入咗數但其實冇。
54. 作為換咗新 iPhone 嘅 **Member**，我想個人預算自動跟返我，咁我唔使重新設定。

## Implementation Decisions

### 架構

- 客戶端係原生 SwiftUI iPhone App。後端係 Supabase（Postgres、登入、實時更新）。後端唔可以依賴 Apple 專屬服務，等之後可以加其他平台。
- 登入經 Supabase Auth。開發階段用 email 驗證碼，因為 Sign in with Apple 要付費嘅 Apple Developer 帳戶；有帳戶之後加 Sign in with Apple，並且可以同現有 email 帳戶連埋。
- 分三個模組：
  - **Ledger 核心**：純 Swift 模組，冇 UI、冇網絡、冇儲存。輸入係一個群組嘅完整狀態同（選填嘅）個人預算，輸出係份額、結餘、建議轉帳、Committed Spend 同 What-if Check 結果。所有金錢規則只喺呢度出現一次。
  - **同步層**：負責同 Supabase 讀寫同訂閱實時更新，並喺部機保留一份唯讀快取畀離線睇。
  - **私人儲存**：個人預算放 SwiftData，只喺部機。有 Apple Developer 帳戶之後加經用戶自己 iCloud 私人數據庫嘅同步。
- UI 只負責顯示 Ledger 核心嘅輸出同收集輸入，唔自己計數。

### 私隱界線

- 個人預算嘅數值永遠唔傳去 Supabase，亦唔出現喺任何 log 或分析事件。
- Committed Spend 同個人層面嘅 What-if Check 只喺裝置上計。Server 知道每個成員每筆份額，但唔知上限，亦唔知邊個超支。
- 群組層面冇任何由個人預算衍生出嚟嘅訊號，包括匿名統計。
- Supabase 用資料列權限：用戶只可以讀寫自己所屬群組嘅資料。

### 金錢

- 只支援港幣。金額一律用整數「仙」儲存同運算，唔用浮點數。
- 平均分除唔盡嗰陣，餘數逐仙派畀頭幾個有份嘅成員（按固定嘅成員次序），確保份額加埋一定等於總數。
- 加一服務費：開咗之後，每個成員嘅份額乘 1.1，四捨五入到仙，差額用同一個餘數規則調整到同總數吻合。

### 提案、出席、選定

- 提案有三個狀態：開放、選定、已轉做開支。一個活動最多得一個選定提案；主辦人可以改揀或者取消選定。
- 提案金額可以係「每人」或者「總數」。「去」嘅人數係覆咗「去」嘅成員數（包括佔位成員）。
  - 每人模式：份額就係嗰個金額；提案總額係金額乘「去」嘅人數。
  - 總數模式：份額係總數除以「去」嘅人數，用同一個餘數規則。
- 對仲未覆或者覆咗「唔去」嘅人，What-if Check 以「假設我去」計，即係人數加埋佢自己。
- 活動要有日期先可以有選定提案。

### What-if Check

- 活動層面：呢個提案嘅總額加埋呢個活動已有開支嘅總額，同活動預算比較。同一活動嘅其他提案唔計。冇定活動預算就冇呢個結果。
- 個人層面：攞提案所屬月份嘅 Committed Spend，扣走同一活動現有選定提案嘅份額（因為佢會被取代），加上呢個提案嘅份額，再同個人預算比較。輸出係剩餘金額，負數即係超支。冇定個人預算就冇呢個結果。

### Committed Spend

- 某個曆月嘅 Committed Spend 等於：開支日期喺嗰個月嘅開支入面我嘅份額，加上活動日期喺嗰個月、我覆咗「去」、而且狀態仍然係「選定」嘅提案入面我嘅份額。
- 提案轉做開支之後狀態變成「已轉做開支」，唔再計入，改為計新開支嘅份額。
- 月份以裝置時區嘅曆月計。

### 結餘同找數

- 結餘跟群組計：每個成員畀出嘅總額減佢所有份額，再加減找數記錄。全組結餘加埋一定係零。
- 建議轉帳用貪心配對（每次配最大債務人同最大債權人）。保證轉帳次數最多係人數減一。唔保證係數學上嘅最少次數，因為嗰個係難解問題。
- 找數只係記錄，App 唔連接任何支付服務。

### 改動記錄

- 開支同找數嘅每次新增、修改、刪除都寫一條改動記錄（邊個、幾時、改前改後），全組可讀。刪除係軟刪除。

### 成員

- 佔位成員同真成員喺帳目上完全一樣，分別只係冇連住用戶帳戶。
- 認領：經邀請連結加入嗰陣，可以揀認領一個現有佔位成員，之後嗰個成員連去佢嘅帳戶，帳目不變。
- 退出：成員同帳戶解除連結，變返佔位成員，帳目不變。

### 通知

- 四種群組通知由 server 喺資料變動嗰陣經 APNs 發出：新提案、提案被選定、有你份嘅新開支、有人記錄咗畀你嘅找數。
- 私人超支警告：server 唔知個人預算，所以判斷唔到邊個超支。做法係每當你喺選定提案嘅份額上升，server 發一個普通嘅「你嗰份變咗」通知；裝置上嘅通知擴充功能用本機嘅個人預算重新計，如果由冇超支變成超支，就將通知內容改寫成超支警告。見 Further Notes 第 1 點。

### 離線

- 冇網絡嗰陣可以睇上次同步嘅資料，所有寫入操作停用並顯示原因。唔做離線寫入佇列。

## Testing Decisions

- 好嘅測試只驗證對外行為：畀一組輸入狀態，檢查輸出嘅數字，唔檢查內部點計。
- **主要測試接縫係 Ledger 核心嘅公開介面。** 所有金錢規則都喺呢度測，用 Swift Testing，唔使模擬器、唔使網絡。要覆蓋：
  - 平均分同逐人金額，包括除唔盡嘅餘數同加一服務費；份額加埋永遠等於總數。
  - 結餘加埋永遠係零；建議轉帳執行完之後全部人結餘歸零，次數唔多過人數減一。
  - 每人模式同總數模式嘅提案換算；出席人數變動之後份額重算。
  - Committed Spend 嘅月份歸屬，包括跨月活動、選定提案轉做開支之後唔重複計。
  - What-if Check：活動層面同個人層面、未覆嘅人以「假設我去」計、冇定預算嗰陣冇結果、取代同一活動現有選定提案。
  - 佔位成員、認領、退出之後帳目不變。
- **第二個接縫係 Supabase 嘅資料列權限。** 對住本機 Supabase 做整合測試：非成員讀唔到亦寫唔到群組資料；退出之後即時失去存取；改動記錄唔可以被改或刪。
- 另外要有一項檢查確認個人預算唔會出現喺任何發去 server 嘅請求入面。
- UI 第一版唔做自動化測試，用 Xcode 預覽同模擬器人手檢查。
- 呢個係全新專案，冇現有測試可以參考。

## Out of Scope

- 提案投票。
- 逐項分單同影單辨識。
- 按比例或份數分帳。
- 多貨幣同匯率。
- 離線記數同衝突處理。
- Android 同網頁版。
- 任何匿名或者公開嘅「有人覺得太貴」訊號。
- App 內過數或者連接 FPS、PayMe。
- SplitLa 以外嘅個人開支記錄。
- 自訂預算週期（例如跟出糧日）。
- Email 驗證碼同 Sign in with Apple 以外嘅登入方法。

## Further Notes

以下幾點係寫 spec 嗰陣先出現、之前傾嘅時候冇定過嘅決定，落手之前值得睇一睇：

1. **私人超支警告同原本講嘅有出入。** 原本定咗「只喺由冇超支變成超支嗰一下通知」。但 server 唔知個人預算，而 iOS 嘅通知擴充功能只可以改寫通知內容，唔可以攔住唔顯示（除非申請到 Apple 嘅特別權限）。所以實際行為係：你喺選定提案嘅份額一升就會收到通知，超支嗰陣內容變成警告。用戶已確認用呢個做法；靜默推送叫 App 喺背景計嘅做法因為 iOS 唔保證送達而被否決。
2. **餘數同服務費嘅進位規則**係我定嘅，冇同用戶確認過。
3. **建議轉帳唔保證係最少次數**，只保證唔多過人數減一。對一般朋友群組嚟講分別好細。
4. **認領佔位成員嘅流程**（加入嗰陣自己揀）係我定嘅。冇防止人認領錯佔位嘅機制，靠改動記錄同群組成員自己發現。
5. **代佔位成員標記出席狀態**係我加嘅，因為份額要用出席人數計。
6. 揀 Supabase 而唔用 CloudKit 或 Firestore，同埋個人預算唔上 server，呢兩個決定未寫成 ADR。
7. **用戶暫時冇付費嘅 Apple Developer 帳戶。** 所以 Sign in with Apple、推送通知、iCloud 同步同埋派畀朋友裝（TestFlight）全部排喺「開 Apple Developer 帳戶」嗰張 ticket 後面。其餘功能喺模擬器同本機 Supabase 度開發同測試。
